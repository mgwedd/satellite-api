# Contributing to Astrea SDA API

Thank you for your interest in contributing to **Astrea SDA API**! We welcome contributions from developers, astrodynamics researchers, space domain awareness specialists, and open-source enthusiasts of all skill levels.

---

## 🏛️ Proof-First Development

To ensure the high performance, physical accuracy, and reliability of our astrodynamics compute engine, we follow a **Proof-First** contribution process:
- **Verification Evidence**: All PRs should include clear evidence demonstrating that changes have been tested and verified. Proof may include unit and integration test results, non-obvious manual verification, visual screenshots, cURL execution traces, or performance benchmarks.
- **Atomic & Focused PRs**: Keep changes focused on a single feature or bugfix. This makes reviews faster, easier to follow, and more helpful for everyone.

---

## 🤖 Guidelines for Working with Coding Agents

We warmly welcome and encourage the use of coding agents and AI development tools to assist your workflow. To keep review queues productive and maintain code quality, please keep the following guidelines in mind:

1. **Review Before Submitting**: Take time to thoroughly review, understand, and test any code generated by assistant tools before opening a Pull Request.
2. **Clear & Concise Descriptions**: Avoid large unedited text dumps or raw AI output in PR descriptions. Write concise summaries highlighting what was changed and why.
3. **Verified Code**: Ensure all submitted logic has been locally tested and verified against project requirements. PRs lacking verification or context may be closed so contributors can refine them before re-submitting.

## 🛠️ Local Development Quickstart

### Prerequisites
- **Rust 1.75+** (`cargo`, `rustc`)
- **Docker** & **Docker Compose**
- **Make**

### 1. Initial Setup
Initialize dev environment, local RSA keypairs (`.keys/`), dev TLS certificates, Git pre-commit hooks, and tools:
```bash
make install-dev
```

### 2. Launch Local Environment
Run the hot-reloading development stack (Postgres + Redis + Nginx Gateway + host `cargo-watch`):
```bash
make dev-hot
```

Or run the full stack containerized inside Docker:
```bash
make dev
```

### 3. Verify Local Build & Test Suite
Before submitting a PR, verify that local checks pass:
```bash
# Run code check and static compilation
make check

# Enforce Rust formatting
make fmt

# Run Clippy lints (zero warnings)
make lint

# Execute full test suite (unit + integration + physics audit)
make test
```

## 📋 Pull Request Process

When submitting a Pull Request:

1. **Use the PR Template**: Fill out the sections in [`.github/PULL_REQUEST_TEMPLATE.md`](.github/PULL_REQUEST_TEMPLATE.md).
2. **Attach Proof of Execution**: Include relevant test output, manual verification details, screenshots, or CLI traces showing your changes in action.
3. **Check Quality Requirements**: Ensure formatting (`make fmt`), linting (`make lint`), and tests (`make test`) pass cleanly.
4. **Preserve API Contracts**: If changing request or response schemas, update the OpenAPI spec (`make openapi`) and verify client SDK alignment.

---

## ⚠️ Breaking Changes & CI Detection

Our CI pipeline automatically detects breaking API contract and schema modifications. If your PR is flagged by automated breaking change detection:

1. **Review Flagged Output**: Verify whether the breaking change was intentional, accidental, or a false positive.
2. **Unintended Breaking Changes**: If unintended, update the PR implementation to maintain full backwards compatibility so CI passes cleanly.
3. **Intentional Breaking Changes**: If intentional and necessary:
   - Request review and explicit approval from the Core Team.
   - Upon approval, the change will be scheduled and merged into the next major version release to prevent disrupting downstream client SDKs and production applications.
4. **False Positives**: If you believe CI flagged a breaking change incorrectly:
   - Provide concrete proof and rationale in the PR description demonstrating why the change is backwards compatible (e.g., non-breaking schema additions, optional fields, or toolchain noise).
   - Tag the Core Team for review to confirm and approve the false positive exception.

## 🧪 Physics & Mathematics Standards

For contributions touching astrodynamics, coordinate transformations, SGP4 propagation, or look angles:
- Validate calculations against authoritative benchmarks (e.g. Vallado *Fundamentals of Astrodynamics and Applications*, Skyfield, or Celestrak test vectors).
- Add unit tests under `tests/physics_audit_tests.rs` verifying tolerance bounds (e.g., GMST within sub-second precision, position vectors within meters).
